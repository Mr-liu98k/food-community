## 2. 表关系（逻辑外键）

```
user 1 ── N recipe（作者）           recipe N ── 1 category（分类）
user 1 ── N recipe_ingredient/step（经 recipe）   ← 主从：recipe 1 ── N ingredient / step
user 1 ── N recipe_like / favorite（经 recipe 多对多打平）
user 1 ── N comment（评论者）       recipe 1 ── N comment
user 1 ── N store_visit（作者）
user 1 ── N reservation（发起人 initiator_id）＋  user 1 ── N reservation（达人 expert_id）
recipe 1 ── N banner（轮播关联，必须审核通过）
user 1 ── N chat_message（from_user_id / to_user_id 双向）
```

**设计决策：全库不建物理 FOREIGN KEY，用「逻辑外键 + 普通索引」**。
理由：应用层保证一致性，删库重建/导数据顺序零烦恼；MyBatis 项目通用做法。唯一例外补偿：`recipe_ingredient`、`recipe_step` 的删除跟随主表 `recipe` 删除走 Service 层先删子表再删主表。

## 3. 审核状态机（recipe / store_visit 共用）

```
待审核(0) ──管理员通过──▶ 已通过(1)
    │
    └──────管理员拒绝(必须填理由)──▶ 已拒绝(2) ──用户修改后重置──▶ 待审核(0)
```

| 规则 | 说明 |
|---|---|
| 前台可见性 | 只有 `status=1` 的菜谱/探店才会出现在前台列表、首页热门、达人主页 |
| 拒绝必填理由 | `status=2` 时 `reject_reason` 非空（后端强校验） |
| 修改重新审核 | 用户编辑已发布内容 → 服务层把状态重置为 `0` 并清空拒绝理由 |
| 轮播约束 | banner 关联的菜谱必须 `status=1`（创建/更新时后端校验） |

## 4. 探店预约状态机（reservation）

```
待处理(0) ──达人同意──▶ 已同意(1)
    │
    └──────达人拒绝(必须填理由)──▶ 已拒绝(2)
```

- 权限边界：**只有被预约的达人（expert_id = 当前用户）** 可以执行同意/拒绝；发起人只读；管理员只读 + 删除。
- 双视角切换：前端按 `direction=initiated | received` 过滤（发起人查 initiator_id，接收方查 expert_id）。

## 5. 关键统计口径（写死在业务层，文档即规范）

| 指标 | 口径 |
|---|---|
| 达人热度 | `SUM(该达人 status=1 的探店 views) * 2`，达人榜按热度降序 |
| 热门菜谱 | `status=1`，按 `views` 降序取前 N |
| 近 7 天发布折线图 | `GROUP BY DATE(create_time)`，**后端以今天为基准补零 7 天**（缺失日期补 0，日期序列服务端生成） |
| 分类饼状图 | `category` 左连 `recipe` 按分类 COUNT（含分类为 0 也返回，图表更好看） |
| 看板四项计数 | `COUNT(recipe 全部) / COUNT(comment) / COUNT(store_visit 全部) / COUNT(reservation 全部)` |
| 聊天会话聚合 | 按"对方"分组取最近一条消息 + `COUNT(is_read=0)` 未读数 |
| 浏览量自增 | 详情页访问时 `UPDATE ... SET views = views + 1`（原子自增，不加锁） |

## 6. 精简决策记录（Ponytail：砍了什么、为什么）

| # | 常规做法 | 本项目做法 | 理由 |
|---|---|---|---|
| 1 | admin 独立一张表 + 独立登录 | **一张 `user` 表 + `role` 字段，一个登录接口**，前端按 role 分流 | 少一套表/拦截器/登录逻辑，管理"管理员"=管理 role=1 的记录 |
| 2 | 聊天建 conversation 会话表 | **只建 `chat_message`，会话列表用 SQL 聚合** | 消息表一张即可推导会话，少一张表 + 少一套同步逻辑 |
| 3 | AI 对话存库（会话记录表） | **后端无状态**，前端维护 messages 历史（最近 10 轮）随请求发送 | 省表省接口，AI"结合上下文"靠历史数组即可达成 |
| 4 | 图片传云 OSS | **本地磁盘 `uploads/` + 静态资源映射**，.env 可切路径 | 毕设环境零成本，接口留好后期换 OSS 只需改一处 |
| 5 | banner / 公告带上下线状态 | **不设开关，删除即下线** | 规格书未要求，少两个字段和一组交互 |
| 6 | 菜谱"置顶 / 推荐位" | **不设置顶，热门按 views 排** | 规格书只要求"热门菜谱" |
| 7 | 点赞/收藏/评论数全冗余 | **只冗余 `likes_count`**（详情页切换频繁），其余实时 COUNT | 冗余一个高频值足够 |
| 8 | 物理外键保证一致性 | **逻辑外键 + Service 层级联** | 见 §2 |
| 9 | 冗余作者昵称/分类名快照 | 一律 JOIN 现查 | 展示数据实时、改昵称/改名不脏历史 |

> 需要说明的是：**达人 = 普通用户 + `is_expert=1`**。管理员设置/取消达人只是改这一个字段，达人榜只统计 `is_expert=1` 且 `role=0` 的用户。
