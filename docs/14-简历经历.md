## 版本四：STAR 面试口述版（用于回答"讲一个你的项目"）

### 项目背景（Situation）

毕设需要独立完成一个全栈项目，我选了美食社区——因为它业务链路完整，**有审核状态机、有权限分层、有实时通信**，能真实暴露问题，而不是一个"增删改查"的玩具项目。

开发过程我采用了 AI 深度协作（Vibe Coding）模式：**决策层（技术选型、业务规则、验收标准）由我把控，实现层交给 AI，验证层由我审查。**

### 我的任务（Task）

1. 完成 6 大模块的全栈实现
2. **建立可重复执行的验收体系**——AI 产出速度快，但"能跑"和"跑对"是两件事
3. 保证交付质量可被验证，而不只是"我看了一眼觉得没问题"

### 我的行动（Action）

**第一步，搭建 4 层验收体系。** 其中审核链路自动化测试是我投入最多的：用 Python 标准库手写 HTTP 客户端（不装 `requests`），因为**验收工具自身的可靠性不能依赖环境**——它在别人机器上、CI 上、答辩现场都必须能直接跑。

覆盖上我刻意做了**全链路 + 边界异常**：正常审核、重复审核、拒绝不填理由、参数越界、未登录、非管理员。最终 **58 项断言，0.7 秒跑完**。

**第二步，从测试失败中辨识真实业务语义。** 初版测试有 7 项连锁失败，我一度以为是系统缺陷。回到业务规则后确认：**审核是一次性动作**，终态记录不能直接改判，必须由用户编辑触发状态重置。**所以我改的是测试用例，不是代码。**

这件事让我确认一个原则：**测试失败有两种可能——代码错了，或者测试写错了。分不清这两者，就会把正确的业务行为当缺陷报出去。**

**第三步，排查 3 个生产级缺陷。** 最难的是"图片上传 100% 报系统繁忙"：我最初的假设（`transferTo` 传绝对路径的坑）**是对的**，但改完依然失败——因为真凶是 `target/*.jar` 只有 193KB，缺 `BOOT-INF/lib`，依赖类在运行期才报 `NoClassDefFoundError`，而它是 Error 不是 Exception，被全局兜底成了"系统繁忙"。

**根因和表象完全无关，突破口是看原始日志而不是继续改业务代码。**

**第四步，把经验固化成机制。** 修完不算完，我把两个坑写进了启动脚本：自动校验 jar 完整性（几百 KB 就重新打包）+ 清理污染的环境变量。**下次不会再踩。**

### 结果（Result）

- 审核链路 **58 项断言全绿**，6 个里程碑验收全部通过
- 独立发现并修复 **3 个生产级缺陷**，全部附完整证据链
- 数据治理：**8 项完整性检查全部归零**，清理 34 个测试遗留账号、补齐 9 张图片
- 产出 **13 份技术文档（2.2k 行）**，含 77 条需求与 78 条测试用例
- 沉淀 1 个可复用的启动自检脚本，从机制上杜绝同类问题

## 附：这份经历可以争取到的追问

面试官大概率会问的，我提前准备：

| 追问 | 我的回答要点 |
|---|---|
| **为什么不用 JUnit / Postman？** | 黑盒验证更贴近集成测试的真实价值；脚本可交付、可接 CI、结果可作回归基线；Postman 手动点出来的结果不可重复 |
| **为什么坚持零依赖？** | 验收工具本身的可靠性不能依赖环境。装 `requests` 才能跑的脚本，在别人机器上就可能跑不起来 |
| **Vibe Coding 怎么保证质量？** | AI 负责实现层，决策层和验证层我自己把控；破坏性操作先 dry-run 预览；**只接受带证据的结论，不接受"应该没问题"** |
| **AI 最大的坑是什么？** | **它不会质疑我的假设。** 我给错方向，它会沿着错误方向高效地做无用功——所以我习惯在让 AI 动手前，先自己确认根因是否唯一 |
| **怎么区分 Bug 和测试写错？** | 回到业务规则本身。我那次 7 项失败，最后确认是测试用例设计错误（审核一次性语义），不是系统缺陷 |
| **鉴权测试有什么坑？** | 本项目鉴权失败时 **HTTP 恒为 200**，错误在响应体 `code` 里。如果只断言 HTTP 状态码，鉴权测试会全部"通过"但全是误判 |

## 附：用词说明（避免面试翻车）

简历上写 **"独立排查并修复"** 而不是"独立开发"——因为代码是 AI 协作产出的，**但缺陷定位、根因分析、验证方案是我独立完成的**。这样表述既诚实，又突出了真正稀缺的能力。

同理，**"主导数据治理"** 比"清理了数据"更能体现工程判断——因为关键在于我识别出了"演示账号不可登录导致无法通过 API 补图"这个设计层矛盾，并明确记录了技术债务，而不是简单粗暴地改数据库。
