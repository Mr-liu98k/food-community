## 1. 项目概述

### 1.1 项目背景

美食爱好者日常面临三类信息割裂：想学做菜要去菜谱站，想找店要去点评站，想提问要去社区问答。
本项目将「菜谱分享 + 探店笔记 + 达人预约 + AI 问答 + 私信交流」聚合到一个平台，并通过
**统一的内容审核流**保证社区内容质量。

### 1.2 建设目标

1. **内容双主体**：菜谱（线上做菜）与探店（线下探店）两条内容线并行，各自独立审核；
2. **角色可生长**：普通用户可被管理员提升为「探店达人」，获得被预约资格；
3. **审核即准入**：所有用户产出的图文内容必须先审核通过才对外可见；
4. **AI 增强**：接入大模型提供流式「AI 美食专家」，降低新手提问门槛；
5. **闭环可验收**：每个里程碑都有可执行验收脚本，功能可量化验证。

### 1.3 术语表

| 术语 | 含义 |
|---|---|
| 菜谱 | 用户发布的图文做菜笔记（`recipe` 主表 + 食材/步骤从表） |
| 探店 | 用户发布的线下店铺体验笔记（`store_visit`） |
| 达人 / 探店达人 | `user.is_expert = 1` 的普通用户，可被其他用户预约探店 |
| 预约 | 用户向达人发起的探店邀约（`reservation`），**双主体**各自有视角 |
| 楼中楼 | 评论支持回复评论，形成层级结构（`parent_id` + `root_id`） |
| 热度 | 达人榜排序指标 = `SUM(该达人审核通过的探店 views) × 2` |
| 双主体审核 | 同一条预约记录，发起方与达人方看到不同视图 |
| SSE | Server-Sent Events，AI 回答的流式推送协议 |

## 2. 用户角色与权限

### 2.1 角色定义

系统**只有一张 `user` 表**，通过 `role` + `is_expert` 两个字段区分身份，不拆表——这样登录只需
一个接口，前端按 `role` 分流到用户端或管理端。

| 角色 | 判定条件 | 说明 |
|---|---|---|
| 游客 | 无 token | 可浏览所有公开 GET 接口 |
| 普通用户 | `role = 0` | 可发布/管理自己的内容、点赞收藏评论、聊天、用 AI |
| 探店达人 | `role = 0` 且 `is_expert = 1` | 普通用户全部权限 + 可接收并处理预约 |
| 管理员 | `role = 1` | 管理端全部功能；**不能删除自己** |

### 2.2 权限矩阵

| 功能 | 游客 | 普通用户 | 达人 | 管理员 |
|---|:---:|:---:|:---:|:---:|
| 浏览菜谱/探店/公告/轮播/达人榜 | ✅ | ✅ | ✅ | ✅ |
| 查看菜谱详情（浏览量 +1） | ✅ | ✅ | ✅ | ✅ |
| 注册 / 登录 | ✅ | — | — | — |
| 发布、编辑、删除自己的菜谱 | ❌ | ✅ | ✅ | ✅ |
| 点赞 / 收藏 / 评论 | ❌ | ✅ | ✅ | ✅ |
| 删除自己的评论（递归删子孙） | ❌ | ✅ | ✅ | ✅ |
| 发起预约 | ❌ | ✅ | ✅ | ✅ |
| 处理预约（同意/拒绝） | ❌ | ❌ | ✅ 仅自己的 | ❌ |
| AI 美食专家 | ❌ | ✅ | ✅ | ✅ |
| 一对一聊天（WebSocket） | ❌ | ✅ | ✅ | ✅ |
| 上传图片 | ❌ | ✅ | ✅ | ✅ |
| 管理端全部（`/api/admin/*`） | ❌ | ❌ | ❌ | ✅ |
| 查看他人「我的内容」 | ❌ | ❌ | ❌ | ❌ |

### 2.3 鉴权规则（实现级）

拦截器 `AuthInterceptor` 作用于 `/api/**`，规则如下：

| 路径 | 规则 |
|---|---|
| `/api/auth/login`、`/api/auth/register` | 白名单，无需凭证 |
| `/api/admin/**` | 必须有效 JWT **且** `role=1`；无 token → `401`，非管理员 → `403` |
| `/api/my/**`、`/api/chat/**` | **GET 也需登录**（私人数据） |
| 其余路径 | GET 放行（游客可浏览）；POST/PUT/DELETE 需有效 JWT |
| `WS /api/ws/chat?token=xxx` | 握手阶段校验 token，失败直接拒绝建立连接 |

> **重要约定**：鉴权失败时 **HTTP 状态码恒为 200**，错误信息通过响应体的 `code` 字段表达
> （`401` / `403`），便于前端统一拦截处理。

## 3. 功能需求

### 3.1 账号模块

| 编号 | 需求 | 规则与约束 |
|---|---|---|
| FR-A01 | 用户注册 | 用户名唯一（重复报「用户名已存在」）；昵称必填；默认 `role=0`；密码 BCrypt 加密存储 |
| FR-A02 | 用户登录 | 用户名 + 密码；密码错误统一提示「用户名或密码错误」（不区分账号是否存在，防枚举）；成功返回 `token` + 用户信息；前端按 `role` 分流 |
| FR-A03 | 查看个人资料 | 返回完整资料（含 `intro`、`createTime`） |
| FR-A04 | 修改个人资料 | 可改昵称 / 头像 / 简介 |
| FR-A05 | 修改密码 | 必须校验旧密码，旧密码错误报「原密码错误」 |
| FR-A06 | 管理员账号自动初始化 | 后端启动时若系统内无管理员，按 `.env` 的 `ADMIN_USERNAME/ADMIN_PASSWORD` 自动创建；**管理员种子不入 SQL** |

**JWT 规格**：载荷 `subject = 用户ID`、`role = 角色`；默认有效期 24 小时；密钥 `JWT_SECRET` **必须 ≥ 32 字符**，否则启动即失败。

### 3.2 首页模块

| 编号 | 需求 | 规则与约束 |
|---|---|---|
| FR-H01 | 轮播图 | 关联菜谱，**仅展示关联菜谱 `status=1` 的轮播**；按 `sort` 升序 |
| FR-H02 | 热门菜谱 | `status=1` 按 `views` 降序，默认 8 条 |
| FR-H03 | 热门探店 | `status=1` 按 `views` 降序，默认 8 条 |
| FR-H04 | 最新公告 | 按 `id` 倒序，默认 1 条 |

### 3.3 菜谱模块

| 编号 | 需求 | 规则与约束 |
|---|---|---|
| FR-R01 | 菜谱分页浏览 | 公开接口**仅返回 `status=1`**；支持按分类筛选、标题关键词模糊搜索 |
| FR-R02 | 菜谱详情 | 主表 + 食材清单 + 步骤 + 作者信息；**每次访问 `views` 自增 1**；登录态额外返回 `liked` / `favorited` |
| FR-R03 | 发布菜谱 | 主表 + `ingredients[]` + `steps[]` **同事务写入**；初始 `status=0` |
| FR-R04 | 编辑菜谱 | 主从表**全量替换**；状态**重置为 0** 并清空 `reject_reason`（改完需重新审核）；`views`/`likes_count` 保留 |
| FR-R05 | 删除菜谱 | 归属强校验（只能删自己的）；级联删除食材/步骤/点赞/收藏/评论 |
| FR-R06 | 点赞 / 取消点赞 | `(recipe_id, user_id)` 唯一键防重复，幂等；同步维护 `likes_count` 冗余计数 |
| FR-R07 | 收藏 / 取消收藏 | `(recipe_id, user_id)` 唯一键，幂等 |
| FR-R08 | 我的菜谱 | 支持 `status` 筛选（0/1/2），展示审核状态与拒绝理由 |
| FR-R09 | 我的收藏 | JOIN 菜谱，仅展示仍存在的菜谱 |
| FR-R10 | 作者主页 | 公开；展示作者资料 + 菜谱数/探店数统计 + 其 `status=1` 的内容分页 |

**菜谱字段校验（后端 Bean Validation）**

| 字段 | 约束 |
|---|---|
| `categoryId` | `@NotNull` 请选择菜谱分类 |
| `title` | `@NotBlank` + 最长 100 字 |
| `cover` | `@NotBlank` **必须上传封面图**（空串会被拒绝） |
| `description` | 最长 5000 字 |
| `ingredients[]` | `@NotEmpty` 至少一种食材；每项 `name`、`amount` 均 `@NotBlank` 且 ≤50 字 |
| `steps[]` | `@NotEmpty` 至少一个步骤；每项 `content` `@NotBlank` 且 ≤2000 字 |

### 3.4 评论模块（楼中楼）

| 编号 | 需求 | 规则与约束 |
|---|---|---|
| FR-C01 | 评论列表 | 按**根评论分页**，每条携带其子评论（`children`）；前端最多展示两层，**存储支持无限层级** |
| FR-C02 | 发表评论 | 支持根评论（`parentId=0, rootId=0`）与回复（指定 `parentId`/`rootId`/`replyUserId`）；回复不存在的评论报「回复的评论不存在」 |
| FR-C03 | 删除评论 | 只能删自己的（他人报「无权删除他人的评论」）；**递归删除其所有子孙评论** |
| FR-C04 | 我的评论 | JOIN 菜谱标题，便于跳转 |

**楼中楼数据模型**：根评论 `parent_id=0 且 root_id=0`；子评论 `root_id` 指向根评论、`parent_id` 指向直接父级；`reply_user_id` 表示被回复人（用于展示「回复 @xxx」）。

### 3.5 探店 / 达人 / 预约模块

| 编号 | 需求 | 规则与约束 |
|---|---|---|
| FR-S01 | 探店分页浏览 | 公开接口仅返回 `status=1`；支持关键词搜索 |
| FR-S02 | 探店详情 | 访问即 `views` 自增 1 |
| FR-S03 | 发布/编辑/删除探店 | 归属强校验；编辑重置为待审核 |
| FR-S04 | 达人榜 | `is_expert=1`；热度 = `SUM(该达人 status=1 的探店 views) × 2`；按热度降序分页 |
| FR-S05 | 发起预约 | 校验目标**必须是达人**（否则「预约对象不是探店达人」）；**不能预约自己** |
| FR-S06 | 我的预约（双视角） | `direction=initiated` 我发起的 / `received` 我接收的 |
| FR-S07 | 处理预约 | **仅被预约的达人**可操作，且仅 `status=0` 可处理；已处理报「该预约已处理，请勿重复操作」 |
| FR-S08 | 拒绝预约 | **必须填写拒绝理由** |
| FR-S09 | 管理员查预约 | 只读（可搜索店铺名/手机号），不能代替达人处理 |

**预约双主体说明**：同一条记录中 `initiator_id` = 发起方，`expert_id` = 被预约达人。
发起方看「我发起的」，达人看「我接收的」，管理员只读全量。

### 3.6 AI 美食专家模块

| 编号 | 需求 | 规则与约束 |
|---|---|---|
| FR-AI01 | 流式问答 | 响应 `text/event-stream`，逐 token 输出，前端打字机效果 |
| FR-AI02 | 多轮对话 | **后端无状态**：前端携带最近历史（最多 10 条），服务端拼接后整体下发 |
| FR-AI03 | 人设注入 | 服务端注入 system prompt，定位「美食社区 AI 美食专家」，要求分条列步骤、不编造不确定信息、默认不超过 400 字 |
| FR-AI04 | 未配置 Key 的降级 | 未设置 API Key 时**后端照常启动**，仅调用该接口返回「AI 服务尚未配置」提示 |
| FR-AI05 | 异常兜底 | 流中断时以一条 SSE 错误事件收尾，不白屏 |

## 5. 核心业务流程

### 5.1 内容审核流（菜谱/探店通用）

```
用户提交  →  status=0 待审核  →  管理端可见、前台不可见
                                    ↓
                          管理员审核
                        ↙            ↘
                 通过 status=1      拒绝 status=2
                       ↓                  ↓
              前台可见/可搜索      用户可见拒绝理由
                                     ↓
                            用户编辑后重新提交
                                     ↓
                            状态重置为 0（循环）
```

**状态机**

| 值 | 含义 | 前台可见 | 备注 |
|---|---|---|---|
| 0 | 待审核 | ❌ | 新建/编辑后自动进入 |
| 1 | 已通过 | ✅ | 可被搜索、可关联轮播 |
| 2 | 已拒绝 | ❌ | `reject_reason` 必填，用户可见 |

### 5.2 预约双主体流程

```
普通用户(发起方)                    达人(接收方)
     │                                  │
     │ ① 发起预约                        │
     ├──────────→ status=0 待处理 ──────→│ ② 我接收的
     │                                  │
     │                                  ├─③a 同意 → status=1
     │                                  └─③b 拒绝(填理由) → status=2
     │ ④ 我发起的（可见处理结果）
     ←──────────────────────────────────┤
                                        │
                          管理员：只读查看全量
```

### 5.3 用户成长为达人的闭环

```
普通用户注册 → 发布菜谱/探店 → 管理员「设为达人」→ 出现在达人榜
                                                        ↓
                              获得「被预约」资格 ← 热度=通过探店views×2
```

### 6.2 关键设计决策

| 决策 | 理由 |
|---|---|
**不建物理外键** | 全表采用「逻辑外键 + 索引」，一致性由 Service 层保证；建库/删库/导入顺序无忧
**单表存三种角色** | 登录只需一个接口，前端按 `role` 分流，避免 admin/user 双表同步问题
**冗余计数** | `recipe.views` / `likes_count` 冗余存储，避免列表页 COUNT 全表
**点赞收藏唯一键** | 用 `uk_recipe_user` 从数据库层杜绝重复点赞，实现天然幂等
**聊天不建会话表** | 一张消息表 + SQL 聚合出会话列表，减少一张表的维护成本
**状态用 TINYINT** | 0/1/2 三态，比字符串省空间且索引效率高

### 6.3 字符集要求

数据库、表、连接三处统一 **utf8mb4 / utf8mb4_unicode_ci**，保证 Emoji 与中文正常存取。

## 7. 非功能需求

| 类别 | 要求 |
|---|---|
| **安全性** | ① 密码 BCrypt 加盐哈希存储，不存明文；② 密钥与数据库凭据一律走 `.env`，**不硬编码、不入库**；③ JWT 密钥强制 ≥32 字符，不满足启动即失败（防止弱密钥上线）；④ 登录失败不区分「账号不存在」与「密码错误」，防账号枚举；⑤ 归属强校验，越权操作一律拒绝；⑥ 上传做扩展名白名单 + 大小限制 |
| **性能** | ① 列表接口全部走 PageHelper 分页，`reasonable=true` 自动矫正越界页码；② 热点字段建索引（status / views / user_id）；③ 冗余计数避免聚合查询；④ 看板接口一次聚合返回，减少往返 |
| **可用性** | ① 未配置 AI Key 时后端仍可正常启动（功能降级而非整体不可用）；② AI 流异常以 SSE 错误事件收尾，不白屏；③ 管理员初始化失败只告警不阻断启动 |
| **可维护性** | ① 分层清晰：Controller / Service / Mapper；② 统一响应结构 `Result<T>` 与分页结构 `PageResult<T>`；③ 全局异常处理器统一兜底；④ SQL 独立在 `sql/` 目录，可重复部署 |
| **兼容性** | 后端 JDK 17+（实际用 21）；前端 Node 18+；数据库 MySQL 8.0+ |
| **可测试性** | 提供 6 个里程碑验收脚本（`scripts/verify-m*.sh`）+ WebSocket 冒烟脚本，覆盖主流程，可一键回归 |
